# 콘텐츠 목록 조회 성능 개선

## 테스트 조건

콘텐츠 기본 목록 조회 API(`/api/contents`)를 같은 0~300 RPS ramp-up 조건에서 비교했다.

- 비교 전 리포트: `k6/reports/content/content-list-0-300rps.html`
- 캐시 적용 후 리포트: `k6/reports/content/content-list-cache-0-300rps.html`
- 대상 API: `GET /api/contents?limit=20&sortBy=createdAt&sortDirection=DESCENDING`
- 부하 패턴: `0 -> 100 -> 200 -> 300 RPS`, 각 1분
- 종료 단계: `0 RPS`로 30초 ramp-down

리포트의 전체 요청 수에는 setup 단계의 로그인 요청이 포함된다. 성능 비교는 실제 측정 대상인 `content-list-default` API별 상세 지표를 기준으로 한다.

## 문제

개선 전 콘텐츠 목록 조회는 요청마다 목록 데이터, 태그, 평점, 리뷰 수, 현재 시청자 수, 썸네일 URL을 조합하면서 DB와 Redis 조회가 반복되는 구조였다.

0~300 RPS ramp-up 부하에서 API 기준 p95 응답 시간이 59,997.81 ms까지 증가했고, 요청 실패율은 64.55%로 측정됐다. 목표 부하를 안정적으로 처리하지 못하고 요청 대부분이 60초 부근에서 지연되거나 실패했다.

## 개선 내용

최신순 목록 조회(`sortBy=createdAt`) 결과를 Redis `contentList` 캐시에 저장하도록 변경했다.

```text
moduply:cache:v3:contentList::null,null,,null,null,20,createdAt,DESCENDING
```

목록 캐시에는 변경 빈도가 낮은 값을 저장한다.

- 콘텐츠 ID
- 콘텐츠 타입
- 제목
- 설명
- 썸네일 URL
- 태그
- 평균 평점
- 리뷰 수

현재 시청자 수는 실시간성이 중요하므로 캐시에 포함하지 않고, 응답 생성 시점에 `WatchingSession` 기준으로 계산해 최종 응답에 조합한다. 여러 콘텐츠의 현재 시청자 수는 Redis pipeline으로 조회해 반복 호출 비용을 줄였다.

리뷰 생성, 수정, 삭제로 평점과 리뷰 수가 갱신되면 `refreshReviewStats()`에서 `contentList` 캐시를 evict한다. 콘텐츠 변경과 리뷰 통계 변경은 명시적으로 캐시를 비우고, 다음 조회에서 최신 값으로 다시 캐싱된다.

또한 부하 테스트 중 Redis 연결 실패를 줄이기 위해 Lettuce connection pool을 활성화하고 `commons-pool2` 의존성을 추가했다. `/api/contents` 반복 INFO 로그와 SQL 로그도 부하 테스트에 영향을 주지 않도록 낮췄다.

## 해석

Redis 목록 캐시 적용 후 같은 0~300 RPS 조건에서 처리량은 10.83 RPS에서 104.98 RPS로 증가했고, 평균 응답 시간은 48.37초에서 184.54 ms로 감소했다. 요청 실패율도 64.55%에서 0.01%로 떨어져 목록 조회 병목이 크게 완화됐다.

다만 캐시 적용 후 API별 p95 응답 시간은 1,052.66 ms로 측정되어, 리포트의 p95 목표인 1,000 ms를 52.66 ms 초과했다. 기존 60초 수준의 지연은 해소됐지만, 300 RPS 구간에서 p95 1초 이내를 안정적으로 만족하려면 Redis pipeline, watcher count 조회, 커넥션 풀, 애플리케이션 인스턴스 리소스 상태를 추가로 확인해야 한다.

현재 테스트 데이터의 대부분은 `thumbnail_url`이 null이며 응답에서는 기본 placeholder URL로 대체된다. 따라서 이번 결과는 실제 운영 썸네일 URL 문자열을 대량으로 내려주는 상황보다 응답 payload가 작을 수 있다.
