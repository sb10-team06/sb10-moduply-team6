## 시나리오 선정 이유

`user-content-browse.js`는 사용자가 콘텐츠를 탐색하는 핵심 조회 흐름을 재현한다.

1. `GET /api/contents`: 커서 페이지네이션 기반 콘텐츠 목록 조회
2. `GET /api/contents/{contentId}`: 목록에서 선택한 콘텐츠 상세 조회
3. `GET /api/reviews`: 선택한 콘텐츠의 최신 리뷰 목록 조회

이 흐름은 메인 콘텐츠 탐색 화면에서 가장 자주 발생하는 읽기 트래픽이다. 쓰기 API 없이 조회 API만 사용하므로, 피크 시간대에 ALB 분산, 애플리케이션 처리량, 콘텐츠 목록 조회 쿼리, 콘텐츠 상세 조회, 리뷰 목록 조회 성능을 확인하기 좋다.

또한 `HOT_CONTENT_RATIO=0.8`을 적용해 전체 콘텐츠에 균등하게 요청을 보내는 대신 인기 콘텐츠에 트래픽이 집중되는 상황을 반영했다. 이 조건은 캐시 효율, 인기 콘텐츠 상세 조회, 특정 콘텐츠 리뷰 조회 인덱스 성능을 함께 검증하기 위한 것이다.

이번 테스트의 1차 목표는 HTTP 기준 약 500 RPS 구간을 안정적으로 통과하는지 확인하는 것이고, 2차 목표는 약 750 RPS 피크 구간에서 p95/p99 지연시간과 병목 지점을 확인하는 것이다.

## 해석

HTTP 실패율은 0.00%이고 체크 성공률은 100.00%지만, 이는 응답이 실패하지 않았다는 의미일 뿐 목표 arrival rate 달성을 증명하지 않는다. `dropped_iterations`는 HTTP 실패나 체크 실패에 포함되지 않으며, 이번 산출물에는 단계별 dropped 값이 없어 “기능 실패 없음”을 피크 구간 처리 성공으로 해석할 수 없다.

전체 집계 기준으로 콘텐츠 목록 API p95는 2768.18 ms, 콘텐츠 상세 API p95는 2004.91 ms, 리뷰 목록 API p95는 1588.31 ms로 모두 목표치를 초과했다. 다만 단계별 API p95/p99가 없으므로 이 지연이 167 RPS 구간에서 이미 발생했는지, 250 RPS 피크 구간에서 급증했는지는 확정할 수 없다.

따라서 현재 결론은 “250 RPS 단계에서 병목 발생”이 아니라 “전체 집계에서 조회 API 지연이 목표를 초과했으며, 피크 구간 달성률과 병목 시점 확인을 위해 단계별 지표를 포함한 재측정이 필요하다”로 정리한다. 다음 실행에서는 단계별 실제 iteration/HTTP RPS, `dropped_iterations`, API별 p95/p99를 Prometheus remote write 또는 stage 태그 커스텀 메트릭으로 수집해야 한다.
